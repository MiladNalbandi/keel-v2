keel Code Review

Review the branch you are on, or anyone's pull request, inside keel. It has the same review window as JetBrains' GitLab and GitHub plugins, plus keel's AI: it explains the change, finds real problems, checks each one again, and you decide what to post.

Based on keel v1 0.80.0 (main 55c798f) and keel v2 0.13.0. Research sources are at the end.

In short

keel v1: /keel:review-pr

It checks a PR against a ticket and your Definition of Done. Then it prints a clear to-do list. The idea is good. But it has two serious bugs:

  • it runs the PR's build code on your computer, with your tokens;
  • some checklist items are marked done or not done by keywords, and you cannot change it.

keel v2: reviews inside its flows

AC review, full-diff review, security and ship lenses, with a fix loop. Strong for keel's own work. But:

  • findings are free text, so real findings get lost and notes become "blocking" and get "fixed";
  • it cannot review someone else's PR, and it posts nothing to GitHub.

The plan

Neither version has the review window that JetBrains' plugin has:

  • the PR list;
  • a file tree;
  • a side-by-side diff with comments on lines;
  • threads you can reply to and resolve;
  • Approve and Request changes.

So we build it in keel v2 as a plugin, Code Review, and add keel's AI on top. After that, the same finding format and the same checks go back into keel v1.

What a good review does

From Google's review guide, the studies, and the AI review tools of 2026 (CodeRabbit, Copilot, Qodo, Greptile, Claude Code Review). Each step has one job:

 your branch  or  PR #212
        │
  1  PREP          no AI · fetch the PR, list files, size, risk, CI checks          (fast, free)
        │
  2  UNDERSTAND    AI · what this PR does, each file in one line, a diagram,
        │               "open these files first", effort 1–5, "split it?" when big
        │
  3  FIND          AI · 2 reviewers in parallel
        │               A: correctness + security      B: tests + ticket/ACs + design
        │
  4  VERIFY        AI · a fresh agent checks every blocking / should-fix claim
        │               → confirmed (kept)  or  rejected (hidden, with why)
        │
  5  YOU DECIDE    read the diff; findings sit on their lines
        │               Add as comment · Edit · Dismiss (say why)
        │
  6  POST          one review on GitHub / GitLab: line comments + Approve / Request changes / Comment
        │
  7  RE-REVIEW     after new commits: only the new diff · open / resolved / new

The review report should have

  1. One verdict line: 2 blocking · 3 should fix · 4 nits · CI ✓ · ACs 4/5 · effort 3/5 · risk medium. It says "No blocking issues" when that is true.
  2. What it does: 2–3 lines, a file table, "start here" files, a diagram when the flow crosses parts.
  3. Ticket check: each AC → met / partly / not met / check by hand, with file:line and the test.
  4. Findings, in this order: blocking, should fix, nits (at most 5), pre-existing (never blocking), questions.
  5. A security part, always there, even when it is empty.
  6. Tests: "would they fail if the code broke?"

Each finding has

  • a short title and a severity (blocking / should fix / nit), as a Conventional Comments label, for example issue (blocking):
  • a category: correctness, security, ticket, tests, performance, design;
  • file:line at the reviewed commit;
  • why it matters, and how it was checked;
  • a suggestion: a small ```suggestion patch only for small fixes, otherwise a prompt for an agent.

Why so strict: 79% of AI comments in one audit were nits nobody wanted. A verify pass and "silent when clean" are what work.

Problems found

I read the code and tested the most serious ones myself. ✓ checked means I saw it happen or saw it in the code.

keel v1

highThe build check runs the PR's code ✓lib/ticket.js:509-532

gradlew, eslint config and tsc come from the PR. They run with your environment (GH_TOKEN, SONAR_TOKEN) and the network, and your node_modules are linked in with write access. Nothing asks first.

highKeyword rules decide checklist items ✓lib/ticket.js:240-266

An item that mentions "database" becomes "met" when no schema file changed. A Mongo .skip(20) counts as a disabled test. You cannot override either.

mediumRe-review after a force-push gets weaker ✓lib/ticket.js:129

The fetch has no +, so it fails. keel falls back to the patch only: no build, no reading files.

mediumA | in a finding breaks it ✓lib/ticket.js:582

TypeScript unions or || move half of the text into the "to do" column.

mediummain is hard-coded ✓agents/code-reviewer.md:11, reviewer.md:11, security-auditor.md:15

Wrong diff on develop or master repos.

mediumBig PRs are reviewed only in part, with no warninglib/ticket.js:318-342

The last group takes everything that is left (9,250 lines in one test). Quality covers only the first 15 files.

keel v2

highReal findings are lost ✓engine/keel_engine/runtime/findings.py:36-39

Two file:line bullets with BLOCKING: yes and no "Blocking" heading become one line: "The reviewer marked this blocking: Security lens on git diff…".

"Checked: auth on /ranks" and non-blocking items count as blocking. In code_review they go to the implementer twice, and no human sees them.

The new plugin: Code Review

Like JetBrains' plugin

  • Review the branch you are on with one click, PR or not.
  • See the pull requests (GitLab: merge requests) with filters: to review, mine, all open.
  • Open one: a file tree with "viewed" marks and comment counts.
  • Side-by-side or inline diff, with the threads on their lines.
  • Comment on a line, reply, resolve.
  • Approve, Request changes or Comment, posted as one review.
  • Check out the branch to run and test it.

Plus keel's AI

  • Overview: what the PR does, each file in one line, a diagram, "open these first", effort and risk, "split it?".
  • Findings: two reviewers, then a verify pass. You see only confirmed findings, on their lines.
  • Every finding: Add as comment (edit first), Dismiss (say why), or Ask KeelBot.
  • Checklist: the reviewer steps, with the ticket's ACs when one is linked.
  • Explain this file and "ask about these lines" in KeelBot.

Safety rules

  • keel reads the PR's code. It never builds or runs it. CI results come from GitHub or GitLab.
  • The AI never posts. A comment goes out only when you press Submit, and you see the text first.
  • Tokens stay in Connections (encrypted). Nothing goes into the image or the repo.
  • The review agents are read only (KeelBot's Ask mode guard).
  • PR text is treated as data, not as instructions.

Reviewer steps

The Checklist tab shows these steps. They come from Google's guide and the review studies (about 60 minutes, about 200–400 lines per sitting).

  1. Broad view (5 min). Read the description, the ticket and keel's overview. Should this change exist at all? If not, say it now. Is CI green?
  2. Ticket (5–10 min). Check every AC marked partly, not met or "check by hand". Read the test of one AC marked met.
  3. Tests first, then "open first" files. Send design comments early, before you read the rest.
  4. keel's findings, blocking first. Add as comment, or dismiss with a reason. You stay responsible: do not approve without reading.
  5. The rest of the diff, plus one security pass. Check auth, input, data exposure and secrets. Look outside the diff where needed.
  6. Write comments. Use Conventional Comments labels, (blocking) or (non-blocking). Say why. Praise good parts.
  7. Decide. Approve when it makes the code better, even if not perfect. Request changes only for blocking items.
  8. Re-review. Only the new commits and the open threads. No new nits after round one.

The keel v1 PR: review-pr: safe and true (0.81.0)

  • Build check off by default. Ask first; run it without your tokens; never link your node_modules with write access.
  • Keyword rules only give hints, never a verdict. An agent decides, and you can override.
  • Base branch from config in every agent. No more main.
  • Fetch with + (force-pushed PRs). Clean up refs/keel/*.
  • JSON findings instead of | lines. Record what verify rejected.
  • Size warning and full coverage of big PRs, or "split it".
  • New: Overview (summary, file table, diagram) at the top of the report.
