keel Product: the screens and the code changes

A product owner writes an idea. keel asks what it needs to know, then helps them go one step deeper each time: brief, impact on the code, decision, a plan per team, and clear tasks for developers. People approve every step, and they can disagree. It is an add-on with its own versions: the developer part does not change. Below: the modes, 15 screens, the agents, the add-on and its versions, every file that changes, and how we build and release it.

Add-on and versions

keel Product is an add-on, with its own versions

The developer part must not break and must not grow. So Product lives in its own folder, builds into its own modules, keeps its own database tables and has its own release line. keel v2 core only gets five small, generic extension points.

keel v2 core

What developers use today

  • engine, API, web, content
  • versions v0.12, v0.13, …
  • image keel-v2:0.13.0 and :latest
  • tests and releases as today
+ 5 extension pointsadd-on loader · root: item · features API · task context and Inbox kinds · menu from features
keel Product add-on

Only where it is installed

  • product/: engine package, API module, web pages, content, own tables
  • versions product-v0.1.0-beta.1, …
  • needs keel 0.13 or newer, below 0.15
  • image keel-v2-product:0.1.0-beta.1, built from keel-v2:0.13.0
QuestionAnswer
Does a developer's keel change?No. Without the add-on there is no Product menu, no product API and no product tables. With the add-on and Product off, the same.
Does the code get bigger for developers?The core grows only by the five extension points. Product pages are their own web chunk and load only when Product is on.
Can Product break a flow?Product never edits core files. It uses the extension points, and those have their own tests in the core suites.
How do the versions work?Core keeps v0.13, v0.14 and so on. Product has product-v0.1.0-beta.1 and so on, and says which core it needs. keel refuses to load an add-on made for another core, with a clear message.
When is it final?Only after every release gate in Phases. Before that: beta and rc tags only, never :latest, Product off by default.
Code changes

Every file that changes

Two parts. In keel v2 core only five small extension points change; each one is generic, tested on its own, and does nothing until an add-on uses it. Everything else is new, in the folder product/.

keel v2 core: five extension points

LayerFileWhat
Engineengine/keel_engine/addons.pynewLoads an installed add-on: its Python package, its content folder (workflows, agents, skills) and its routes. No add-on installed: nothing happens.
Engineworkflows/model.py, runtime/compiler.pychangedroot: item on a parallel step: each item runs in its own folder, read only. Useful for developers too, for example one reviewer per service.

How it looks in code

Four examples

A product workflow (YAML)

# product/content/workflows/product-impact.yaml
id: product-impact
scope: product        # runs on an initiative, not in one repo
steps:
  - { id: repos, kind: code, action: "product:repos" }
  - id: analyse
    kind: parallel
    from: repos
    root: item         # each analyst: its own repo, read only
    agent: impact-analyst
    instructions: >-
      Read the brief, and the objection if there is one.
      Find what this change touches in your repo: files,
      APIs, data, events. Use the knowledge base, the code
      graph and the team pages. Write what you do not know
      as UNKNOWN, never as safe.
  - { id: merge, kind: code, action: "product:save-doc",
      with: { doc: impact } }      # a new version
  - { id: ask, kind: code, action: "product:questions" }
  - { id: leads, kind: gate,
      ask: "Each lead confirms, corrects or disagrees" }

Data and flow

One thread from idea to commit

Every story knows its initiative, every task knows its story, and every keel flow knows its task. So progress rolls up, history is complete, and a developer can always see why.

Where things live: documents and team pages as Markdown in a small product repo (for example initiatives/INI-12/brief.md), so changes are reviewed like code and have git history. Jira is the mirror the teams already use. The add-on's own tables hold the state, links, questions, history and follow-ups.

How we build and release it

Every Product release is a beta until it is fully tested

Phase 0 · about 2 weeks

Prototype, no code change

  • The product workflows and 4 agents as content, in a "product" project
  • Clarify questions as the first steps
  • The repos added as projects, read only
  • Output: Markdown documents; Jira by hand

Done when one real feature goes from idea to plan and the leads say the impact is right. Nothing is released.

Phase 1 · about 6 weeks

Extension points, then the beta

  • Core v0.13: the 5 extension points, all core tests unchanged and green
  • product-v0.1.0-beta.1: modes, screens, clarify, questions, disagree, plan, Jira, runs, history, follow-ups, team knowledge, presentation

Done when a PO runs one initiative end to end in keel-lab, and the developer suites still pass untouched.

Phase 2 · 6–8 weeks

Team mode, opt-in

  • Users and roles: PO, PM, lead, developer, viewer
  • Sign-in (OpenID Connect), Postgres
  • Each person's own Inbox and View
  • A developer's keel links to the shared keel
  • Off by default: a one-person keel works as today

Done when three teams use one shared keel in the beta. Release: product-v0.2.0-beta.N.

Phase 3 · pilot, then final

Pilot and outcome loop

  • One real team for 2–4 weeks
  • The outcome check after release
  • Estimates learn from history
  • Fix what the pilot finds

Done when every release gate below passes. Only then product-v1.0.0.

Release gates before product-v1.0.0

  1. Core is untouched: the engine, API and web suites of keel v2 pass without any change to their tests.
  2. Product suites pass: engine tests with the fake model for every workflow, API tests with the stub engine, web tests.
  3. Versions match: the add-on is tested against the core version it says it needs.
  4. Real run: a throw-away keel-lab on 2–3 scratch repos, end to end.
  5. Pilot: one real team for 2–4 weeks, with no blocking bug open.

Until all five pass: only -beta.N or -rc.N tags, never :latest, and Product is off by default.
